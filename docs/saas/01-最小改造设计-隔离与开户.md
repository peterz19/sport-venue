## 0. 目标与非目标

### 目标（合格线）

1. 平台 ADMIN 可开户、启停商户，并查看商户概况  
2. 商户 A / B 数据互不可见（含改 ID 试探）  
3. 商户停用后，其下账号无法登录  
4. 商户账号不能调用平台开户/全量商户接口  

### 非目标（本设计不做）

- 订阅套餐、到期扣费、独立域名/白标  
- 每商户独立库 / 独立部署  
- 功能开关与配额（留给迭代 C，本文仅预留扩展点）  
- C 端小程序/公众号真实对接（留给迭代 D；本文 **§5.4 定字段与落点**，本阶段可不建表）

## 1. 角色与租户模型

| 主体 | 标识 | 登录入口 | 数据范围 |
|------|------|----------|----------|
| 平台管理员 | `User.userType=ADMIN`，`merchantId=null` | `/auth/login` → Admin 前端 | 全平台 |
| 商户老板 | `B_MERCHANT` + `merchantId` | `/auth/merchant/login` | 本商户 |
| 商户店员 | `B_STAFF` + `merchantId` | 同上 | 本商户（业绩等按既有规则收窄） |

**租户主键：** 继续使用 `merchants.id`（Long）作为 `merchant_id`。  
**对外展示码：** 已有 `merchants.merchant_code`，开户可生成；不另建 tenant 表。

```text
平台 ADMIN
   └── 管理多个 Merchant
         ├── User(B_MERCHANT / B_STAFF)
         ├── Venue / Court / Product / Team / Booking / Sales...
         ├── merchant_wx_channels（小程序 / 公众号 AppId+Secret，预留）
         ├── merchant_wx_pay（C 端支付商户号，预留）
         └── 业务行全部带 merchant_id
```

## 3. 迭代 A：硬隔离 + 关停

### 3.1 API 权限矩阵（改造后）

#### 3.1.1 匿名（permitAll）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/auth/login` | 平台登录 |
| POST | `/auth/merchant/login` | 商户端登录 |
| GET | `/health/**` | 健康检查 |
| GET | `/swagger-ui/**`、`/v3/api-docs/**` | 文档（生产可再关） |

#### 3.1.2 仅 ADMIN

| 前缀 / 路径 | 说明 |
|-------------|------|
| `/merchants/**` | 商户列表、详情、开户、改状态、改资料 |
| `/venues` 写操作（POST/PUT/DELETE） | 平台代建/改/删场馆（建议） |
| `/venues` 列表不带强制租户 | 平台可按 `merchantId` 筛选全量 |
| 后续平台汇总 API | 如 `/admin/stats/**`（新建时同样仅 ADMIN） |

> **建议：** 将「平台场馆管理」与「商户场馆管理」语义分开：  
> - Admin 继续用 `/venues/**`（仅 ADMIN）  
> - 商户只用 `/business/venues/**`（强制本商户）  
> 当前 Security 把 `/**` 开给多种角色，**必须收紧**。

#### 3.1.3 商户侧（B_MERCHANT / B_STAFF；ADMIN 可调试进入）

| 前缀 | 规则 |
|------|------|
| `/business/**` | 必须已登录且为 B 端角色（或 ADMIN 模拟，见下） |
| 数据过滤 | **一律** `merchant_id = JWT.merchantId`；忽略请求体/Query 中的外来 `merchantId`（ADMIN 除外，见 3.2） |

#### 3.1.4 建议禁止或收紧

| 现状 | 改造 |
|------|------|
| `/**` 对 `B_MERCHANT/B_STAFF/C_USER` 过宽 | 改为：未匹配路径默认 **deny** 或仅 ADMIN |
| 商户可调 `GET /merchants` | 改为仅 ADMIN |
| 商户可调 `GET /venues?merchantId=他人` | 商户禁止走该入口；或强制改写为本人 ID |

#### 3.1.5 SecurityConfig 目标伪代码

```text
permitAll: auth 登录、health、swagger
/merchants/**          → ROLE_ADMIN
/venues/**             → ROLE_ADMIN          // 平台场馆
/business/**           → ADMIN | B_MERCHANT | B_STAFF
/auth/logout、/auth/user/info → 已认证
anyRequest             → denyAll 或仅 ADMIN
```

（若 Admin 前端还有其它通用路径，列入 ADMIN 白名单，避免误伤。）

### 3.2 租户上下文约定

| 场景 | `merchantId` 来源 |
|------|-------------------|
| `/business/**` 读写 | **仅 JWT**（`SecurityUtils.requireMerchantId()`） |
| 请求体带 `merchantId` | **丢弃/覆盖**为 JWT 值 |
| Query `merchantId`（B 端） | **忽略**；列表接口不开放跨商户筛选 |
| ADMIN 调 `/business/**`（可选） | 不允许无商户上下文瞎调；或禁止 ADMIN 调 business，平台只用 `/venues`/`/merchants` |
| ADMIN 调 `/venues?merchantId=` | 允许，用于平台筛选 |

**实现要点（设计约束，非代码）：**

- 在 `Business*Controller` 或统一 `TenantGuard`：进入业务前绑定 `TenantContext.merchantId`  
- Repository 查询禁止「无商户条件的全表扫」出现在 business 路径  
- 按 ID 读详情：先查实体，再校验 `entity.merchantId.equals(ctx)`，否则 404（推荐）或 403

### 3.3 登录与关停闭环

#### 3.3.1 商户登录 `/auth/merchant/login`

校验顺序：

1. 用户名密码正确  
2. `userType ∈ {B_MERCHANT, B_STAFF}`  
3. `user.status = ACTIVE`  
4. `user.merchantId != null`  
5. **新增：** 加载 `merchants` 行，`status = ACTIVE`（`INACTIVE` / `SUSPENDED` → 拒绝，文案：「商户已停用，请联系平台」）  
6. 签发 JWT（claims：`userId, userType, merchantId`）  

#### 3.3.2 平台登录 `/auth/login`

1. 仅允许 `ADMIN`（建议收紧：Admin 前端不应再用商户账号登录）  
2. `user.status = ACTIVE`  
3. JWT 无 `merchantId` 或为 null  

#### 3.3.3 停用商户

Admin：`PUT /merchants/{id}/status` → `INACTIVE` / `SUSPENDED`

生效方式（最小）：

| 方式 | 说明 |
|------|------|
| **登录拦截**（必须） | 见 3.3.1 第 5 步 |
| Token 已签发 | 最小方案：短 JWT 过期 + 业务请求可选二次校验商户状态；完整方案：登出黑名单 / 版本号（可后置） |

**建议最小二次校验：** 在 `JwtAuthenticationFilter` 或 `TenantGuard` 中，对 `/business/**` 每次请求（或缓存 1～5 分钟）确认商户仍 ACTIVE；停用后最多延迟一个缓存窗口失效。

#### 3.3.4 停用单个员工

保持现有：`user.status=INACTIVE` → 不可登录；**不影响**商户整体状态。

### 3.4 越权防护用例（测试用例即设计）

| # | 操作 | 期望 |
|---|------|------|
| 1 | 商户 A token 调 `GET /merchants` | 403 |
| 2 | 商户 A token 调 `POST /merchants/onboard` | 403 |
| 3 | 商户 A 用 B 的 `bookingId` 调详情/取消 | 404/403 |
| 4 | 商户 A 请求体伪造 `merchantId=B` 创建商品 | 仍写入 A |
| 5 | 停用商户 A 后 A 老板登录 | 失败 |
| 6 | 停用 A 后 B 一切正常 | 通过 |

## 4. 迭代 B：开户体验 + 审计

### 4.1 开户向导（产品流程）

```text
步骤1 商户资料 → 步骤2 老板账号 → 步骤3（可选）首场馆 → 完成
```

| 步骤 | 字段（必填加粗） |
|------|------------------|
| 商户 | **name**，merchantCode（可空自动生成），merchantType，contactName/Phone，address |
| 老板 | **ownerUsername**，**ownerPassword(≥6)**，**ownerRealName**，ownerPhone |
| 首场馆（可选） | **name**，**type/spaceType/chargeType**，**address**，capacity，open/closeTime |

**事务：** 商户 + 老板 (+ 场馆) 同一事务；任一步失败整单回滚。

**完成页展示：** merchantId、merchantCode、ownerUsername（密码仅当时可见，不落审计明文）。

现有 `POST /merchants/onboard` 可扩展可选 `firstVenue` 对象；或拆 `POST /merchants/onboard` + `POST /venues`（ADMIN）两步由前端向导串联——**推荐扩展 onboard 可选场馆**，减少半成品商户。

### 4.2 商户详情（Admin）

只读聚合：

- 商户基础信息、状态  
- 老板账号（username、realName、status）  
- 场馆数量、员工数量（店员+老板）  
- 最近开户/启停审计条目  

接口建议：`GET /merchants/{id}/overview`（仅 ADMIN）

### 4.3 平台操作审计

#### 新表 `platform_audit_logs`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | |
| action | VARCHAR(40) | `MERCHANT_ONBOARD` / `MERCHANT_UPDATE` / `MERCHANT_STATUS` / `VENUE_CREATE_FOR_MERCHANT` … |
| target_type | VARCHAR(20) | `MERCHANT` / `USER` / `VENUE` |
| target_id | BIGINT | |
| merchant_id | BIGINT | 可空（纯平台动作） |
| before_json | TEXT | |
| after_json | TEXT | |
| operator_id | BIGINT | 平台管理员 |
| operator_name | VARCHAR(50) | 快照 |
| remark | VARCHAR(200) | |
| create_time | DATETIME | |

**不记密码明文。** 开户 after_json 可含 ownerUsername、merchantCode，不含 password。

写入点：onboard 成功、update、updateStatus、（若向导建场馆）建馆成功。

列表：`GET /merchants/{id}/audits` 或 `GET /admin/audits?merchantId=`（仅 ADMIN）

### 5.4 迭代 D 预留：每商户 C 端微信（强烈建议独立表，勿堆在 merchants）

> **产品前提：** 每个商户绑定自己的 **公众号 + 小程序**，C 端用户在该商户小程序登录后订场、充值。  
> **原则：** AppId/Secret 是租户级密钥；`access_token` 是运行时缓存；openid 按 App 隔离。  
> **本阶段：** 只定表结构与落点；**可不建表**，但开户/详情 UI 与 API 设计必须预留入口，避免以后改 `merchants` 大宽表。

#### 5.4.1 推荐新建 `merchant_wx_channels`（渠道凭证）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | |
| merchant_id | BIGINT NOT NULL | 租户；建议 UNIQUE(merchant_id, channel_type) |
| channel_type | VARCHAR(20) | `MINI_PROGRAM` / `OFFICIAL_ACCOUNT` |
| app_id | VARCHAR(64) NOT NULL | **全局 UNIQUE**（C 端请求靠 appId → 商户） |
| app_secret_enc | VARCHAR(512) | 加密存储；API **永不回显明文** |
| oa_server_token | VARCHAR(64) | 公众号服务器配置 Token（校验签名） |
| oa_encoding_aes_key | VARCHAR(64) | 公众号消息加解密（可选） |
| bind_status | VARCHAR(20) | `UNSET` / `BOUND` / `INVALID` |
| remark | VARCHAR(200) | |
| create_time / update_time | DATETIME | |
| update_by | BIGINT | 平台操作人 |

**不要**把以下内容长期落在 `merchants` 宽表上：

| 项 | 建议落点 |
|----|----------|
| access_token / expires_at | **Redis**（如 `wx:at:{channelType}:{appId}`），DB 最多作兜底缓存列（可选，默认可不做） |
| refresh 逻辑 | 服务内 `WxTokenService`，按商户 channel 取 secret 调微信 |

#### 5.4.2 推荐新建 `merchant_wx_pay`（充值/支付，可与渠道同迭代或稍后）

订场充值会用到支付商户号，与登录 AppId 不同，建议另表：

| 字段 | 说明 |
|------|------|
| merchant_id | PK/UK |
| mch_id | 微信支付商户号 |
| mch_api_v3_key_enc | APIv3 密钥（加密） |
| mch_serial_no / cert 路径或密文 | 商户证书 |
| notify_url_suffix | 回调路径后缀（完整 URL = 平台域名 + merchant 标识） |
| status | ACTIVE/INACTIVE |

> Phase 1 收银仍是 B 端扫码占位；此表为 **C 端充值/订场支付** 预留，与 `docs/b-end-sales` Phase 2 支付可共用设计，但密钥按 **商户隔离**，禁止全局一份 yml。

#### 5.4.3 C 端用户身份预留 `user_wx_identities`

openid **随 AppId 变化**，不能只在 `users` 上挂一个 openid：

| 字段 | 说明 |
|------|------|
| id | PK |
| merchant_id | 租户 |
| channel_type / app_id | 哪个小程序/公众号 |
| openid | UNIQUE(app_id, openid) |
| unionid | 可空；同一开放平台下跨公众号/小程序打通 |
| user_id | 关联平台/C 用户表（可后置） |
| create_time | |

与已有订场预留对齐：`bookings.source=C` + `customer_user_id` → 指向该 C 用户。

#### 5.4.4 `merchants` 表是否加列？

| 方案 | 结论 |
|------|------|
| 直接在 `merchants` 加 `mp_app_id` / `mp_secret` / `oa_app_id`… | **不推荐**（密钥易随 Merchant DTO 泄露；扩展差） |
| 仅加汇总列 `wx_mini_bound` TINYINT、`wx_oa_bound` TINYINT | **可选**，方便 Admin 列表展示「已绑定/未绑定」，真值仍以 channel 表为准 |

#### 5.4.5 需要改动/预留的**位置清单**

| # | 位置 | 怎么预留 |
|---|------|----------|
| 1 | **DDL** | 迭代 D 或 SaaS 迁移：`merchant_wx_channels`（必）、`merchant_wx_pay`（充值时）、`user_wx_identities`（C 登录时）；可选 `merchants.wx_*_bound` |
| 2 | **实体/Repository** | `MerchantWxChannel` 等；**不要**把 secret 映射进现有 `Merchant` 对外 DTO |
| 3 | **Admin API** | `GET/PUT /merchants/{id}/wx-channels`（仅 ADMIN）；PUT 写 secret，GET 只返回 appId + bindStatus + 脱敏 |
| 4 | **开户向导（迭代 B 扩展）** | 步骤可增加「可选：绑定小程序/公众号」；也可开户后在详情页配置——**推荐后者**，避免阻塞开户 |
| 5 | **Admin 商户详情 overview** | 展示：小程序 AppId（脱敏）、公众号 AppId、绑定状态；入口「配置微信」 |
| 6 | **平台审计** | action=`MERCHANT_WX_BIND` / `MERCHANT_WX_UPDATE`；after_json 只含 appId/channelType，**禁止 secret** |
| 7 | **C 端登录入口（未来）** | `POST /c/auth/wx-login`：入参 `appId` + `code` → 查 channel → code2session → 写/查 `user_wx_identities` → 签发 C JWT（claims 含 `merchantId`） |
| 8 | **租户解析** | 小程序请求：**禁止**信前端传的 merchantId；**只信** appId→channel→merchant_id；停用商户则拒绝 C 登录 |
| 9 | **支付回调（未来）** | URL 带 `merchantId` 或 `mchId` 反查 `merchant_wx_pay`；验签用该商户密钥 |
| 10 | **Security** | `/c/auth/**` permitAll；`/c/**` 业务需 C 登录；微信渠道配置接口仅 ADMIN |
| 11 | **商户端（:3001）** | 默认**不展示、不编辑** AppSecret（防店员泄露）；若产品要商户自助，仅老板 + 二次验证，且审计 |
| 12 | **配置中心/环境变量** | 仅放「平台级」项（如第三方代开发 component_appid）；**每商户密钥进 DB（加密）+ 主密钥进环境变量**，禁止提交仓库 |
| 13 | **与 bookings 预留关系** | 已有 `source`/`customer_user_id` 足够接 C 订场；充值流水另表时同样带 `merchant_id` + `customer_user_id` |

#### 5.4.6 租户解析示意

```text
C 小程序启动
  → 携带本小程序 appId（或后端用 code2session 返回的 appid）
  → merchant_wx_channels.uk(app_id) → merchant_id
  → 校验 merchants.status=ACTIVE 且 channel.bind_status=BOUND
  → 后续订场/充值全部带该 merchant_id（JWT）
```

#### 5.4.7 决策摘要

| 点 | 决策 |
|----|------|
| 字段放哪 | **独立 `merchant_wx_channels`**，不进 `merchants` 宽表 |
| AppId | 全局唯一，作为 C 端租户路由键 |
| Secret / 支付密钥 | 加密存储；列表/详情脱敏；审计不记明文 |
| access_token | Redis，不进商户主表 |
| 开户是否必填微信 | **否**；B 端可先营业，C 端开通时再绑 |
| 公众号 vs 小程序 | 两行 channel，或同商户两类型各一条 |
| 第三方平台代开发 | 若日后统一授权，可加 `auth_type=SELF\|COMPONENT` 与 `authorizer_refresh_token`；本期按「商户自有 AppId/Secret」预留即可 |

| 项 | 改动 |
|----|------|
| 请求 | 不传、不信任本地篡改的「切换商户」 |
| 登录失败 | 展示「商户已停用」专用文案（后端错误码约定，如 `code=40301`） |
| 微信配置 | 默认不做；密钥归平台 Admin |

---

## 7. 错误码约定（建议）

| code | 含义 |
|------|------|
| 401 | 未登录 / token 无效 |
| 403 | 角色不符（如商户调平台 API） |
| 40301 | 商户已停用 |
| 40302 | 账号已停用 |
| 404 | 资源不存在或不属于本商户（统一 404 防探测） |

---

## 8. 实施顺序建议

```text
1. SecurityConfig 收紧 + 冒烟（商户调 /merchants 必须 403）
2. 登录校验 merchants.status
3. business 路径 TenantGuard / 忽略外来 merchantId
4. 详情接口从属校验
5. （B）onboard 可选首场馆 + platform_audit_logs
6. （B）Admin 商户详情 overview
7. 按 §3.4 用例做自动化或手工验收清单
```

---

## 9. 验收清单（A+B 合并）

**隔离**

- [ ] A 看不到 B 的商品/订单/订场/球队/员工  
- [ ] A 伪造 ID 访问 B 资源 → 404/403  
- [ ] A 调 `/merchants/**` → 403  

**关停**

- [ ] 停用 A 后老板/店员均不可登录  
- [ ] 已登录 token：在二次校验启用后，business 请求失败  

**开户**

- [ ] 开户生成商户 + 老板，可用商户端登录  
- [ ] 可选首场馆后，商户端「我的场馆」可见  
- [ ] 审计中有 ONBOARD 记录且无密码  

**平台**

- [ ] 仅 admin 账号可进 Admin 并开户  
- [ ] 商户列表、启停、详情正常  

---

## 10. 风险与决策

| 点 | 决策 |
|----|------|
| ADMIN 能否调 `/business/**` | **建议禁止**，平台与商户入口分离，减少误操作 |
| 停用是否踢在线 token | 最小：登录拦截；增强：请求期校验商户状态 |
| 历史脏数据（同商户重名场馆等） | 不阻塞 SaaS；隔离与关停优先 |
| C_USER / 旧 `/**` 角色 | 本阶段收紧 deny；C 端另案 |
| 每商户微信密钥放哪 | **独立 channel 表 + 加密**；不进 `merchants` 宽表；C 端用 appId 路由租户 |
