# 收银支付接入设计 · 付款码被扫（扫码枪）

> 状态：**仅设计，未开发**  
> 日期：2026-07-28  
> 场景：B 端收银台选品确认后，顾客出示微信/支付宝**付款码**，商户用**扫码设备**扫入完成收款  
> 对照现状：当前仅现金确认 + 扫码占位；`merchant_wx_pay` 表已预留；无真实支付通道  
> 相关：`b-end-sales/01`（产品曾规划「主扫」出码）· `saas/00`（每商户支付凭证）

---

## 0. 先回答你的三个问题

### 0.1 现在有没有接支付？

**没有。** 现状是：

| 能力 | 状态 |
|------|------|
| 现金支付 | ✅ 已实现 |
| 屏幕出示收款码（顾客扫你） | ❌ 仅 UI 占位 |
| 扫码枪扫顾客付款码 | ❌ 未做 |
| 真实微信/支付宝资金流 | ❌ 未做（C 端充值也是 MOCK） |

### 0.2 你要的模式叫什么？

你描述的是 **「被扫 / 付款码支付」**：

```text
顾客打开微信/支付宝 → 出示「付款码」
        ↓
商户扫码枪扫入一串数字（条码/二维码内容）
        ↓
系统调支付通道「付款码扣款」接口
        ↓
成功则订单 PAID
```

这和早期收银文档里的 **「主扫」**（屏幕出二维码、顾客扫你）**不是同一条产品路径**。  
本设计以 **被扫（扫码枪）为主路径**；主扫可作为二期可选项并列说明。

### 0.3 还要额外接什么？有费用吗？

- **必须有**：收款主体资质 + 微信/支付宝商户能力（或聚合支付服务商）+ 公网可达的异步通知（部分场景）+ 扫码枪硬件  
- **费用**：通道按交易额抽成（常见约 **0.38%～0.6%** 量级，以实际签约为准）+ 可选服务商服务费 + 扫码枪硬件成本；平台软件本身无强制「通道年费」，但服务商可能有开户/服务费  

下文逐步展开。

## 1. 目标与非目标

### 1.1 目标

1. 收银台选品 → 确认收款 → 进入收款页  
2. 收银员用扫码枪扫描顾客微信/支付宝付款码 → 一次扣款  
3. 成功自动完单；失败可重试或改现金  
4. 多商户 SaaS：每家商户用**自己的**收款商户号（或挂在服务商子商户下）  
5. 报表可区分：现金 / 微信 / 支付宝  

### 1.2 非目标（本期不做）

- 顾客扫屏幕静态码/动态码（主扫 Native）— 列为可选二期  
- 分账到多个收款方、信用卡分期、会员储值与通道打通（C 端钱包另案）  
- 自研扫码枪驱动（用键盘模式即可）

## 2. 两种扫码别搞混（决策）

| | **被扫（本期主推）** | **主扫（原 Phase2 设想）** |
|--|---------------------|---------------------------|
| 谁出码 | 顾客付款码 | 商户收款码（屏幕） |
| 设备 | **扫码枪必选** | 屏幕即可，枪可选 |
| 接口形态 | 微信付款码支付 / 支付宝条码支付 | Native/预下单出码 + 回调/轮询 |
| 操作体感 | 扫一下就扣，适合柜台 | 顾客举手机扫屏幕 |
| 与你描述 | ✅ 一致 | ❌ 不一致 |

**产品决策（建议锁定）：**

> 收银 Phase 2 = **被扫优先**；现金保留；主扫作为 Phase 2.5 可选增强。

## 3. 接入路线怎么选（三选一）

这是费用和你要准备材料差最大的分叉。

### 方案 A：直连微信 + 直连支付宝（自建双通道）

```text
venue-service → 微信支付 API（付款码）
              → 支付宝开放平台（条码支付）
```

| 优点 | 缺点 |
|------|------|
| 无中间商抽成（仅官费） | 要分别进件、分别对接、分别对账 |
| 资金清分清晰 | 开发量大；每商户都要有两套资质 |
| | 小微场馆进件门槛、审核周期 |

适合：平台或大型连锁自己有支付团队、商户少且规范。

### 方案 B：聚合支付 / 收单服务商（强烈推荐首版）

```text
venue-service → 一家聚合服务商 SDK/API
                    ├─ 微信
                    └─ 支付宝
```

常见类型（举例，非推荐品牌）：收钱吧、拉卡拉、随行付、汇付、星驿付、Pay 类 SaaS 等。  
SaaS 场馆系统常用：**服务商报备子商户**，每家场馆一个子商户号。

| 优点 | 缺点 |
|------|------|
| 一套 API 覆盖微信+支付宝 | 可能多一层服务费率或年费 |
| 进件、对账、设备方案成熟 | 绑定服务商生态 |
| 很多提供扫码枪/音箱配套 | 需评估结算周期与客服 |

适合：**你现在的多商户 SaaS** —— 一家场馆一个收款账户，平台统一技术对接。

### 方案 C：智能收银硬件整机（一体机厂商）

买「收银机 + 已集成支付」的整机，你们只做订单同步。  

| 优点 | 缺点 |
|------|------|
| 硬件+支付打包快 | 业务深度绑定硬件；多商户定制难 |
| | 与现有 Vue 收银台整合成本可能更高 |

适合：单店快速开张；不太适合你们已有 Web 收银台的架构。

---

### 推荐结论

| 阶段 | 建议 |
|------|------|
| **现在落地** | **方案 B：选 1 家聚合/收单服务商**，先打通「被扫」 |
| 远期 | 若体量大、要降费率，再评估直连或更换服务商（PaymentGateway 抽象可替换） |

## 4. 你需要提供什么（清单）

分三层：**平台公司**、**每家场馆商户**、**技术环境**。

### 4.1 平台侧（你 / 软件公司）要准备

| # | 材料/能力 | 说明 |
|---|-----------|------|
| 1 | 营业执照等主体资质 | 与服务商签「服务商/ISV」或「平台」合同 |
| 2 | 对公账户 | 收服务费或作为服务商结算户（视模式） |
| 3 | 联系人、法人、网站/APP 说明 | 进件用；说明「体育场馆收银 SaaS」 |
| 4 | 公网 HTTPS 域名 | 接收支付结果通知（即便被扫同步返回，异步通知仍建议接） |
| 5 | 服务器出口 IP | 部分通道要加白名单 |
| 6 | 隐私与资金安全说明 | 不存完整付款码；密钥加密（已有 `SecretCrypto` 方向） |
| 7 | 选择并签约一家支付服务商 | 拿到：商户号/机构号、AppId、密钥、文档、测试环境 |

### 4.2 每个场馆商户要准备（进件）

| # | 材料 | 说明 |
|---|------|------|
| 1 | 营业执照 / 个体户证件 | 收款主体 |
| 2 | 法人身份证 | 进件实名 |
| 3 | 结算银行卡（对公或法人结算卡） | 钱打到哪 |
| 4 | 门店照片、收银台照片、场地照片 | 微信/支付宝风控常要 |
| 5 | 经营类目 | 体育场馆/文体娱乐等，影响费率与审核 |
| 6 | 联系人手机号 | 签约短信、商户平台 |
| 7 | （若直连微信）微信支付商户号 + API 证书 | 方案 A 才需要每户齐全 |
| 8 | （若直连支付宝）支付宝 PID/应用 + 密钥 | 同上 |

**SaaS 运营含义：** Admin 开户后，要有一步「支付进件/绑定子商户」；未完成进件的商户只能继续现金。

### 4.3 门店设备

| 设备 | 是否必须 | 说明 |
|------|----------|------|
| **扫码枪** | ✅ 被扫必选 | 建议支持一维码；微信/支付宝付款码多为数字串 |
| 收银电脑/平板 | ✅ | 现有商户端浏览器即可 |
| 云音箱/小票机 | 可选 | 播报「微信到账 xx 元」；很多服务商套装含音箱 |
| 摄像头刷脸 | 不需要 | 本期不做刷脸 |

**扫码枪接入方式（推荐）：**

- 默认 **USB 键盘模式（HID）**：扫完等于键盘敲入一串数字 + 回车  
- 收银台收款页放一个隐藏/聚焦的输入框，监听回车即提交付款码  
- **无需**单独装厂商 SDK（除非用服务商定制枪）

## 5. 还要额外接入什么？

### 5.1 必接

| 系统 | 用途 |
|------|------|
| 聚合支付或微信+支付宝开放平台 | 真正扣款 |
| （服务商）商户进件 / 子商户开通 API 或后台 | 每场馆收款账户 |
| 你们自己的 `PaymentGateway` 实现 | 把通道结果落到 `sales_orders` / `sales_payments` |

### 5.2 强烈建议接

| 系统 | 用途 |
|------|------|
| 支付异步通知 URL | 同步超时/用户密码中的补单 |
| 查单接口 | 前端「支付中」轮询或人工点「查询」 |
| 对账文件 / 日终对账 | 财务核对，防漏单 |
| 退款接口（可二期） | 收银错单、当日退货 |

### 5.3 不必先接

- 分账、营销券、信用卡、跨境  
- 与 C 端小程序支付同一套「JSAPI」—— **柜台被扫和 C 端小程序支付是不同产品能力**，可共用商户号，但接口不同

## 6. 费用怎么构成（统计口径）

> 下列为**行业常见量级**，以你最终签约合同为准；设计阶段用于预算，不是报价单。

### 6.1 通道费（必有）

| 项目 | 常见情况 |
|------|----------|
| 微信/支付宝交易手续费 | 大约 **0.38%～0.60%** / 笔（餐饮零售类目常见约 0.38% 起；文体类目以审核为准） |
| 谁承担 | 通常从结算款中扣；商户实收 = 成交额 − 手续费 |
| 结算周期 | T+1 常见；部分 D+1 / T+0 加价 |

### 6.2 服务商 / 平台相关（方案 B 可能有）

| 项目 | 常见情况 |
|------|----------|
| 服务商加收 | 有的「官费 inclusive」、有的再加 **0.0x%～0.1%** 或打包年费 |
| 开户/进件费 | 有的免费，有的按商户收一次性费用 |
| 短信/电子签 | 少量 |
| SaaS 软件费 | 你们自己定（与支付通道无关） |

### 6.3 硬件

| 项目 | 常见情况 |
|------|----------|
| 普通 USB 扫码枪 | 约几十～两百元量级 |
| 服务商定制枪 + 音箱套装 | 可能押金或购机，看活动 |

### 6.4 你们研发/运维成本（内部）

| 项 | 粗估 |
|----|------|
| 对接被扫 + 查单 + 回调 + Admin 进件状态 | 约 1～2 周（有经验）～ 3～4 周（含联调进件） |
| 每换一家服务商 | 再计一轮适配（故 PaymentGateway 要抽象） |

### 6.5 费用归属建议（产品规则）

| 费用 | 谁出 |
|------|------|
| 交易手续费 | **场馆商户**（从货款扣） |
| 扫码枪 | 场馆自购，或平台批量采购转售 |
| 服务商年费（若有） | 可平台承担或向商户收「支付开通费」 |
| 软件订阅 | 平台商业模式另定 |

## 7. 在你当前系统里怎么挂（架构）

### 7.1 现状可复用点

| 已有 | 用法 |
|------|------|
| `sales_orders` / `sales_payments` | 继续作为订单与支付流水 |
| 收款页 UI | 改「等待扫码枪输入」为主，弱化占位二维码 |
| `PaymentGateway` 扩展点（方案已写） | 新增 `BarcodePayGateway`（被扫） |
| `merchant_wx_pay` | 可扩展为「支付通道配置」或改为 `merchant_pay_channels` |
| SaaS 租户隔离 | 支付必带 `merchant_id`；回调按商户验签 |
| Admin 商户详情 | 增加「支付进件状态 / 子商户号」 |

### 7.2 目标链路（被扫）

```text
商户端收银台
  → POST 创建销售单（PENDING）
  → 收款页：输入框自动聚焦，提示「请扫描顾客付款码」
  → 扫码枪录入 authCode + 回车
  → POST /business/sales/orders/{id}/pay/barcode
        body: { authCode: "130...或28..." }
  → venue-service
        1. 校验订单 PENDING + 本商户
        2. 读该商户支付配置（子商户号等）
        3. 调服务商「付款码支付」
        4. 成功：订单 PAID + sales_payments（WECHAT/ALIPAY）
           用户输密码中：返回 PAYING，前端轮询查单
           失败：保持 PENDING，提示重试/改现金
  → 异步 notify（可选加固）：再次幂等完单
```

### 7.3 与现金并存

```text
收款页
  ├─ 主操作：扫付款码（被扫）
  └─ 次操作：现金支付（现有接口保留）
```

同一订单：**只能成功支付一次**（幂等）；已 PAID 再扫码必须拒绝。

### 7.4 通道抽象（方便换服务商）

```text
PaymentGateway
  ├── confirmCash(order)                    // 已有
  ├── payByAuthCode(order, authCode)        // 本期新增 · 被扫
  ├── queryPay(order / paymentNo)           // 查单
  ├── handleNotify(raw)                     // 回调
  └── (可选) createNativeQr(order)          // 二期主扫
```

配置按商户：

```text
merchant_pay_profile
  merchant_id
  provider          // AGGREGATOR_X / WECHAT_DIRECT / ALIPAY_DIRECT
  sub_mch_id        // 子商户号
  status            // UNAPPLIED / AUDITING / ACTIVE / DISABLED
  ...密钥密文
```

（可在现有 `merchant_wx_pay` 上扩展字段，或新建一表；实现阶段再定。）

## 8. 产品交互步骤（收银员视角）

| 步 | 动作 | 系统 |
|----|------|------|
| 1 | 选品、改数量 | 现有 |
| 2 | 点「确认收款」 | 创建 PENDING 订单，进入收款页 |
| 3 | 看金额，请顾客打开付款码 | 页面大字金额 +「请扫描付款码」 |
| 4 | 扫码枪扫顾客手机 | 输入框收码，自动提交 |
| 5a | 成功 | 成功页，播报/展示「微信/支付宝 ¥xx」 |
| 5b | 需要用户输入密码 | 显示「等待顾客确认…」，轮询 2～3 秒 |
| 5c | 失败（余额不足等） | 提示原因，可重新扫或改现金 |
| 6 | 顾客付现金 | 点「现金支付」走现有流程 |

**注意：** 付款码有时效（常约 1 分钟），超时需顾客刷新后再扫。

## 10. 风险与合规

| 风险 | 应对 |
|------|------|
| 重复扣款 | 商户侧订单号唯一；支付流水唯一；接口幂等 |
| 同步超时实际已扣款 | 必须查单 + 异步通知补单 |
| 付款码被日志泄露 | 禁止打全码；禁止入库长期保存 |
| 商户未进件就收款 | 功能开关或 `pay_profile.status!=ACTIVE` 时禁用被扫 |
| 二清违规 | **不要**平台先收再分给商户；用服务商子商户或直连商户号，钱进商户自己的结算卡 |
| 退款纠纷 | 二期做退款；一期可先「当日现金退、系统备注」 |

「二清」是监管红线：平台不能把多商户货款先进自己对公再私下转。应用 **服务商 + 子商户** 或 **商户直连**。

| 6 | 扫码枪谁采购？ | 商户自购 USB 键盘枪，平台给型号建议 |

## 15. 补充：直连（方案 A）与「平台抽成 / 资金归集」说明

> 背景：产品倾向采用 **方案 A（直连微信 + 支付宝）**，并希望「钱先进总账户 → 扣通道费 + 平台抽成 → 再日结到各商户卡」。  
> **结论先说清楚：后半句这种资金归集日结，不是微信/支付宝「系统自带」的普通能力；在未持有支付牌照时，很容易构成违规「二清」。**

### 15.1 钱默认怎么走（直连商户号）

若每家场馆各自开通 **微信支付商户号 / 支付宝商户**：

```text
顾客付款
  → 微信/支付宝清算
  → 直接结算到「该场馆商户号」绑定的银行卡
  → 通道手续费由微信/支付宝在结算时扣除
```

- **不会**自动先进你的「平台总账户」  
- 平台抽成 **不会**自动扣  
- 你们系统只负责下单、被扫、记流水；**资金清算在微信/支付宝侧**

这是合规默认模型，也是「直连 A」最常见落地方式。

### 15.2 你理解的「总账户归集再分」是什么

```text
顾客付款 → 先到平台对公总户 → 你们算手续费+抽成 → 再打给各商户卡
```

| 问题 | 说明 |
|------|------|
| 微信/支付宝会不会自带？ | **不会。** 普通商户 API 不提供「帮你代收再随意下发」 |
| 算不算二清？ | **高风险。** 无支付牌照时，平台代收商户货款再下发，监管上通常视为支付业务/二清 |
| 系统自己写日结转账？ | 用对公网银批量打款 ≠ 合法收单；风险在主体与合规，不在会不会写代码 |

**因此：抽成与分钱，不能靠「先收进自己户再转」来做（除非有牌照或持牌合作方）。**

### 15.3 平台抽成想可控，合规做法是什么

需要把「抽成」做成支付侧认可的 **分账 / 抽佣**，而不是私下截留。

| 做法 | 钱怎么走 | 抽成可控？ | 备注 |
|------|----------|------------|------|
| **每商户独立商户号，抽成线下结算** | 货款全额进商户卡；商户另付软件费/抽成给你 | 合同可控，资金流简单 | 实现最简单；抽成靠账单+对公收款，不经支付通道 |
| **服务商/平台 + 子商户 + 官方分账** | 交易进子商户（或按规则分账）；按比例分给平台商户号 | ✅ 比例/金额在下单或分账时设定 | 实质更接近「持牌体系内的分账」，常要申请微信/支付宝**服务商或分账产品** |
| **合作持牌机构（银行/支付公司）** | 由持牌方清分 | ✅ | 你们做业务系统，清分外包 |

对「AICODING、研发可控」：**写代码快，解决不了牌照问题**；分账要申请产品权限、签补充协议、按规则上报分账接收方。

### 15.4 「扣费我可控吗」分别指什么

| 费用 | 谁定 | 你能否控 |
|------|------|----------|
| 微信/支付宝通道手续费 | 微信/支付宝（类目、资质） | **基本不可随意改**；可申请优惠/选对类目，不能在系统里「设成 0」 |
| 平台抽成（软件佣金） | 你与商户的合同 | ✅ 可控；落地要用上面合规方式，而不是总账户截留 |
| 结算周期 T+1 等 | 支付机构 | 一般不可随意改；部分产品可升级（可能加价） |

### 15.5 和方案 A 怎么组合（建议决策）

既然坚持 **直连 A**，推荐两档：

**A1 · 最低合规复杂度（建议先做支付收款）**

1. 每商户自己的微信商户号 + 支付宝商户号（或先只做微信）  
2. 被扫收款，钱进商户自己卡  
3. 平台抽成：**按月对账后，商户对公付给平台**（或平台开票收软件费）  
4. 系统内可配置「抽成比例」仅用于**账单展示与应收统计**，不自动截流  

**A2 · 要自动抽成再日结到商户**

1. 向微信/支付宝申请 **服务商 / 分账（或电商收付通等适用产品）** 能力  
2. 每笔或按规则：货款按比例入商户、抽成入平台商户号  
3. 结算仍由微信/支付宝打到各方银行卡——**不是你们系统自己日终打款**  
4. 研发要对接：分账接收方、分账指令、回退、对账；进件与审核周期显著变长  

**不要做的：** 平台一个总商户号收所有馆的钱，再自行日结打卡。

### 15.6 系统自带 vs 你们要单独处理

| 能力 | 谁负责 |
|------|--------|
| 扣微信/支付宝通道费 | 支付机构自动扣，系统只需记账展示 |
| 钱打到商户卡 | 支付机构结算，**不是**你们写「日终打款」 |
| 平台抽成自动分走 | **官方分账产品** 或 **线下收软件费**；需单独申请/运营，不是收银被扫默认自带 |
| 被扫下单、查单、对账展示 | 你们系统开发 |
| 配置抽成比例、出平台应收报表 | 你们系统可做（A1 做「应收」；A2 才对接真实分账） |

### 15.8 已确认：采用 A1 + 平台抽成应收台账

**决策（2026-07-28）：**

- 支付通道：方案 **A 直连**（微信 + 支付宝被扫），货款进各商户自己结算卡  
- 平台收入：方案 **A1**——系统累计「平台抽成应收」，**日结 / 月结 / 年结**均可；结清后应收清零（或结转到下一期），**必须保留操作记录与结算快照**  
- 不做：总账户归集二清；首期不做官方分账 A2  

#### 名词（务必分开）

| 名称 | 含义 | 谁收 |
|------|------|------|
| 通道手续费 | 微信/支付宝费率，结算时已从商户货款扣 | 微信/支付宝 |
| **平台抽成（佣金）** | 你与商户约定的软件/平台费，按下单额或净额×比例 | 你的平台公司 |

下文「未收手续费」在产品上应写作 **「未结平台抽成 / 应收佣金」**，避免和通道费混淆。

#### 台账模型（合理且建议落地）

```text
每笔线上支付成功（PAID）
  → 按商户抽成规则计算 commission_amount
  → 写入佣金明细（待结算）
  → 商户维度：未结抽成余额 += commission_amount

日结 / 月结 / 年结（运营在 Admin 发起）
  → 选定商户 + 账期（或「截至当前全部未结」）
  → 生成结算单快照：含订单明细汇总、比例、应收合计、操作人、时间
  → 商户线下对公打款（或标记已收款）
  → 结算单状态 = SETTLED，对应明细标记已结
  → 未结余额减少（可清零该账期）；历史快照与操作日志永久保留
```

#### 关键规则

| 规则 | 说明 |
|------|------|
| 只统计线上真实支付成功单 | 现金单是否抽成单独配置（默认可不抽或抽） |
| 结清按「结算单」不是裸清零 | 必须绑定账期与明细快照，禁止无快照直接把余额改 0 |
| 已结明细不可改金额 | 改比例只影响新单；争议用红冲/调整单 |
| 操作审计 | 谁、何时、结了哪段、金额、凭证号（选填） |
| 周期灵活 | 同一套「结算单」支持按日/月/年或自定义区间 |

#### 这样是否合理？

**合理。** 优点：合规、实现简单、日结月结年结共用一套模型、审计完整。  
商户量大后再评估是否升级 A2 自动分账；台账模型可继续保留作对账。
